# 補完元の容量制限と Git プロンプトの計測

4 MiBを超える補完元を読む前に拒否すると、16 MiBの入力の中央値は28.29 msから13.22 ms、最大常駐メモリの中央値は23,314,432バイトから6,307,840バイトへ下がった。通常の小さい補完元は30.11 msと29.29 msだった。

生データは [maintenance-2026-11-12.json](maintenance-2026-11-12.json) に記録した。

## 比較条件

Darwin arm64、Rust 1.99.1、release（opt-level=3、LTO、codegen-units=1）で比較した。両方のバイナリは依存更新後の同じ Cargo.lock を使い、今回の実装修正前と修正後を別名で保存した。各ケースで両方を交互に3回ウォームアップし、交互に7回ずつ計測した。ほかの作業も実行している環境で、Git の計測には10 ms程度の標準偏差がある。

## 補完元の容量

一時ディレクトリに設定・キャッシュ・状態を分離し、未インストールの `example` コマンドをファイル方式で登録した。入力は `#compdef example` と `_arguments '--flag[Test]'` を持つ小さい有効なファイルと、先頭に `#compdef example` を置いて16 MiBに伸ばした疎なファイルである。

```sh
/usr/bin/time -l "$binary" completion-refresh --force
```

毎回強制更新するため、失敗の待機時間やキャッシュの再利用で測定が短くならない。有効な入力では両方が `updated` を返し、サイズ超過では両方が4 MiB上限のエラーを返すことを確認した。経過時間はプロセスの起動から終了まで、メモリは macOS の `time -l` の maximum resident set size（バイト）を使った。

## Git の確認処理の費用

1,000ファイルをコミットした変更なしのリポジトリで、Git だけを表示する `prompt` を交互に3回ウォームアップし、7回ずつ計測した。Python の `time.perf_counter_ns` で CLI の起動から終了までを測った。設定と状態は一時ディレクトリへ分離し、Git のシステム・グローバル設定も無効にした。出力は変更前後で一致した。

中央値は75.09 msから84.59 msになった。設定キーを取得して外部フィルターを無効にするため、Git の起動が1回増える。fsmonitor・属性フィルター・署名検証・不足オブジェクトの自動取得を、プロンプトの表示だけで実行しないための費用として採用した。フィルターを使うファイルやサブモジュールの表示上の制約は、[設定リファレンス](../configuration.ja.md#git-表示の制約)に記載している。

履歴検索は `scripts/bench_history.py` で1,000件と10万件の7ケースを交互に7回測定し、変更前後の出力がすべて一致することを確認した。生データの `history` に計測値と出力ハッシュを保存した。
